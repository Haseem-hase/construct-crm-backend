Construct CRM backend study notes
=================================

Lesson 1. What happens when someone uses the CRM?
-------------------------------------------------

You can start here even if you have never read code. Imagine a site supervisor
opens a project and uploads two progress photos. The screen is the frontend.
The backend is the part of the CRM that receives the request, checks who sent
it and what they can do, and saves the information. The database keeps
records such as project names, account details, and links to photos.

Follow one request through the files
------------------------------------

1. Start in src/modules/projects/project.routes.ts. Find the line starting
   with router.patch. PATCH means "change some details of an existing
   record." The project ID in the address tells the backend which job the
   supervisor wants to change. The checks on that line run in order.
2. authenticate checks who is signed in. authorize checks whether that
   person can update projects. Then uploadProjectImages receives the files.
   Look for maxFiles to see how many files this upload accepts.
3. project.controller.ts receives the incoming details and asks for the
   update. project.service.ts applies the rules for changing the job.
   project.repository.ts contains steps that read or write database records.
   prisma/schema.prisma describes what information those records can hold.
4. Read the // Study: line above each code line as you go. Start with the
   comments for the overall steps and skip the punctuation on your first
   read. A closing brace } marks the end of a group. It often ends a group
   of steps that belong to the same check or action.
5. Try reading src/modules/auth/auth.routes.ts next. Find POST /login.
   Before the sign-in handler runs, validate(loginSchema) checks the submitted
   details. The full address is /api/auth/login. Look in src/app.ts for /api
   and src/routes/index.ts for /auth to see how the address is assembled.
6. Once those examples feel familiar, try inventory. Find issueInventoryRequest
   in inventory-workflow.service.ts. Imagine a warehouse issuing tools to a
   site. Look for the steps that find the request, change the available stock,
   and add a record of the movement.

Words you will see beside the code
----------------------------------

Request / response. The message the screen sends and the reply it gets.
Route. An address and action that tell the backend which work to do.
Middleware. A step shared by routes, such as checking a sign-in.
Controller. Takes the incoming message, asks for the work, and replies.
Service. Applies business rules, such as which stock can be issued.
Repository. Groups the steps used to read or save records.
Record / field. Think of one row in a register and one detail on that row.
ID. A value that identifies a record, such as a project or company.
Prisma. The tool this backend uses to talk to the database.
Zod. The tool used to check whether submitted information looks right.
TypeScript. The language used here. Its types describe the kinds of values
the code expects, such as text, a number, or a group of details.
Function / return. A named or reusable step and the result it gives back.
const / await. Give a value a name. Wait for some work to finish.
if / !. Run a step only if a check passes. A leading ! reverses a check.
Token. A pass the app sends as proof that someone is signed in.
Transaction. A group of database steps treated as one job. If the write fails,
the database can undo the changes made within that job.

Where the backend starts
------------------------

src/server.ts opens the door for requests. src/app.ts sets up shared request
handling. src/routes/index.ts directs each request to the right feature.
Those three files make more sense after tracing one feature above.

Project files and local infrastructure
--------------------------------------

package.json defines the npm scripts and dependency ranges. dev runs the
TypeScript server in watch mode, build compiles it, and start runs the compiled
server. package-lock.json records resolved dependency versions for repeatable
installation. JSON does not support slash comments.

tsconfig.json configures TypeScript. It targets ES2022 and uses NodeNext module
rules. Strict checks are enabled. The normal build reads src and writes dist.
The generated JS in dist and installed packages in node_modules can be rebuilt
from the source and dependency files.

docker-compose.yml describes a PostgreSQL 17 service, maps host port 5432 to
the container port, reads the database settings from environment variables,
and mounts a named volume so database files can survive container replacement.
YAML uses # for comments.

.env supplies local environment values. Read src/config/env.ts and
prisma.config.ts for the code that consumes environment settings. Keep actual
local values private. .gitignore controls which local paths Git normally
excludes. uploads holds uploaded media. .DS_Store stores Finder metadata.

migrate.exp is an Expect helper. Its spawn command launches another process,
expect waits for matching output or completion, and send supplies input to the
process. Expect scripts use Tcl syntax.

prisma.config.ts connects the Prisma CLI to the schema and migration directory.
prisma/schema.prisma defines the current models. prisma/seed.ts creates initial
application data. prisma/migrations/migration_lock.toml records the PostgreSQL
provider for the migration history.

Reading the migration history
-----------------------------

Each entry below names a folder under prisma/migrations. Open its migration.sql
to see the actual SQL. Reading the migrations in timestamp order shows how the
current schema evolved. Prisma tracks checksums for applied SQL files, so the
study notes for migrations live here.

CREATE TYPE defines allowed enum values. CREATE TABLE declares columns and
constraints. ALTER TABLE changes an existing table. A foreign key enforces a
link between records, and ON DELETE controls what happens to dependent rows.
A UNIQUE index also rejects duplicate keys. A partial index applies only to
rows meeting its WHERE condition. INSERT INTO can seed or backfill data.

  provide the two parts of a permission such as PROJECT and VIEW.

  Creates the organizations table and its uniqueness rules.

  Adds the nullable organizationId to users. ON DELETE SET NULL allows the
  user row to remain when its referenced organization is removed.

20260829211216_add_customers
  Creates organization-owned customer records and indexes their lookup fields.

20260830081412_add_projects
  Creates projects and the ProjectStatus enum. Compare its original customer
  link with the later project-customer migration.

20260830082407_add_project_members
  Adds a project/user membership table and the enum for membership roles.

20260830082901_add_project_labour
  Adds an early project-to-labour link using user records. The dedicated labour
  model later replaces this arrangement.

20260831082104_add_organization_roles
  Adds ROLE and USER permissions and introduces organization scoping for roles.

20260901194952_role_architecture
  Introduces organization_roles as a link between organizations and role
  templates. Users and permission assignments reference this link.

20260901200804_add_role_organization
  Adds organization ownership back to role templates. Also introduces the
  nullable SystemRole on users for SUPER_ADMIN.

20260907200909_init_customer
  Expands customers with types and a parent-customer link, plus a sequence used
  in customer setup.

20260907201204_add_parent_customer_index
  Indexes the parent-customer field for lookups of child records.

20260908181100_customer_hierarchy_cascade
  Uses both parentCustomerId and organizationId for the foreign key. This
  keeps a child and its parent in the same organization and cascades deletion.

20260909195205_add_customer_contact
  Adds contact records under customers. A partial unique index limits customers
  to one primary contact apiece.

20260913205107_init_project_customer
  Introduces the project-customer join table and relationship types such as
  OWNER and CLIENT. Also expands project fields, including actual dates.

20260914185642_remove_legacy_project_fields
  Drops older project fields and the original direct customer link after the
  join table was introduced.

20260917201446_add_labour_and_profession
  Creates dedicated labour and profession records. Compare the new tables
  with the project_labour structure removed by this migration.

20260917212809_add_unique_labour_phone_per_organization
  Enforces unique labour phone numbers inside each organization.

20260918174020_init_contractor_phase_1
  Creates contractors, their status enum, and the sequence and indexes for
  contractor records.

20260918180321_add_contractor_module
  Adds CONTRACTOR to Module so it can form part of a permission.

20260918182258_init_contractor_project_assignments
  Adds contractor placements, the responsibility catalog, and a join table
  assigning responsibilities to a placement.

20260920211054_init_labour_assignment
  Adds labour placements associated with contractor project assignments and
  tracks their status.

20261031120000_inventory_foundation

20261031130000_inventory_location_warehouse_scope
